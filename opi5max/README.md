# Orange Pi 5 Max: загрузка с NVMe через SD-карту

Хост `o5`, 192.168.10.53. Ubuntu 24.04 (сборка Joshua Riek, ядро 6.1.0-1026-rockchip)
на Samsung 990 PRO 4TB, около 82 docker-контейнеров.
Настроено и проверено 2026-09-18.

## Проблема

После резкого отключения питания плата зависала и не видела NVMe. Помогала только
загрузка с microSD и штатное выключение, после которого диск снова определялся.

Причина найдена в коде загрузчика и подтверждена замерами:

* Samsung 990 PRO после грязного выключения восстанавливает внутренние таблицы и
  около 7 секунд не отвечает на первую admin-команду. Замер после реального обрыва
  питания 2026-09-18: 7.07 секунды.
* NVMe-драйвер U-Boot ждёт ответа 6 секунд (`ADMIN_TIMEOUT 60`, то есть 6e6 мкс в
  `nvme_submit_sync_cmd`) и **не повторяет попытку**.
* Код одинаков в вендорском U-Boot 2017.09 из SPI-флеша и в mainline 2025.04.
  Перепрошивка SPI сама по себе не лечит.
* Штатное выключение Linux шлёт диску NVMe shutdown notification, поэтому после
  него диск готов сразу. Отсюда и работавший ручной обходной путь.

Диск исправен. Дело в гонке между готовностью диска и терпением загрузчика.

## Решение

microSD постоянно стоит в слоте. Когда карта вставлена, BootROM отдаёт управление
U-Boot с карты (2025.04 из Armbian), а не прошивке из SPI. Проверяется так:

```
tr -d '\0' < /proc/device-tree/chosen/u-boot,version
```

В `boot.cmd` на карте добавлен блок `NVMe handoff`:

1. `pci enum`, пауза 5 секунд. Этого хватает, чтобы диск уложился в лимит 6 секунд.
2. До шести попыток `nvme scan` с паузой 3 секунды между ними.
3. `bootflow scan -lbG nvme` грузит Ubuntu через её собственный
   `/boot/extlinux/extlinux.conf` на NVMe. Ядро, initrd и параметры берутся с NVMe,
   поэтому обновления ядра Ubuntu подхватываются сами и на карте синхронизировать
   нечего.
4. Если диск так и не прочитался, стартует спасательный Armbian с карты. Служба
   `nvme-handoff-recover` ждёт, пока Linux увидит диск, и делает чистую
   перезагрузку. Это та же ручная процедура, только автоматическая. Не больше трёх
   попыток подряд, защита от цикла по отпечатку суперблока ext4.

Результат работы загрузчика виден в командной строке ядра: `nvme_handoff=booting`,
`nvme_tries=N`, `nvme_flags=...`.

NVMe из спасательной системы никогда не монтируется и не пишется.

## Разделы карты

| Раздел | ФС | Метка | Назначение |
| --- | --- | --- | --- |
| `mmcblk1p1` | ext4 | `armbi_root` | спасательный Armbian, там же `boot.cmd` и `boot.scr` |
| `mmcblk1p2` | vfat | `HANDOFF` | флаги, журнал попыток, инструкция |

Раздел `HANDOFF` создан 2026-09-18 в свободном хвосте карты, размер 197 МБ.
Раздел `armbi_root` при этом не трогали.

## Флаги

Пустые файлы в корне раздела `HANDOFF`:

| Флаг | Что делает |
| --- | --- |
| `force-sd` или `force-sd.txt` | всегда грузить спасательную систему с карты |
| `try-nvme-once` | вместе с `force-sd`: один раз загрузить NVMe, U-Boot сам удалит флаг перед попыткой |
| `dry-run` | проверить NVMe, но загрузить спасательную систему |

Нет флагов означает обычный режим, загрузку Ubuntu с NVMe.

Вариант `force-sd.txt` нужен, чтобы флаг можно было создать с Mac: macOS не любит
файлы без расширения в графическом интерфейсе.

Из спасательной системы удобнее утилитой:

```
nvme-handoff status | auto | force-sd | once | dry-run
```

## Проверено

| Проверка | Итог |
| --- | --- |
| Сухой прогон `dry-run` | U-Boot нашёл диск с первой попытки, загрузился спасательный Armbian |
| Штатная загрузка через карту | Ubuntu с NVMe, 82 из 82 контейнеров |
| Реальный обрыв питания | Ubuntu поднялась сама, спасательный режим не понадобился |

Подробности реального обрыва: диск готовился 7.07 секунды, U-Boot прочитал его с
первой попытки, ядро стартовало через 36 секунд после обрыва, дальше около двух
минут шла плановая полная проверка ext4, Postgres восстановился штатно.
Ошибки ядра совпадают с загрузкой от 2026-08-29 через старый загрузчик.

## Диагностика

```
tr -d '\0' < /proc/device-tree/chosen/u-boot,version   # какой U-Boot дал управление
tr ' ' '\n' < /proc/cmdline | grep nvme_               # что решил блок handoff
cat /media/jr/HANDOFF/nvme-retry.txt                   # пишется, если попыток было больше одной
sudo tail /media/jr/armbi_root/var/lib/nvme-handoff/recover.log   # автоперезагрузки
```

## Откат

В спасательной системе:

```
cp /boot/boot.cmd.armbian-orig /boot/boot.cmd
mkimage -C none -A arm -T script -d /boot/boot.cmd /boot/boot.scr
systemctl disable nvme-handoff-recover
```

Резервные копии на карте, в `/root/nvme-handoff-backup`: оригинальный `boot.cmd` и
`boot.scr`, таблица разделов карты, дамп SPI-флеша на 16 МБ.

Если просто вынуть карту, плата вернётся к старому поведению: SPI U-Boot 2017.09
грузит NVMe напрямую. Работает, пока диск выключали штатно.

## Установка на новую карту

Разделы, один раз, из спасательной системы:

```
echo "start=7340032, type=EBD0A0A2-B9E5-4433-87C0-68B6B72699C7, name=handoff" \
  | sfdisk --append --no-reread /dev/mmcblk1
partx -a --nr 2 /dev/mmcblk1
mkfs.vfat -F 32 -n HANDOFF /dev/mmcblk1p2
```

Значение `start` подбирается по свободному хвосту конкретной карты,
смотреть `sfdisk -F /dev/mmcblk1`. Сначала прогнать с `--no-act`.

Файлы: скопировать каталог `sd-card` на спасательную систему и запустить
`install-files.sh`. Скрипт ставит утилиты и службу, кладёт инструкцию на оба
места и пересобирает `boot.scr`.

## Что осталось на твоё решение

* **Автомонтирование карты в Ubuntu.** Рабочий стол монтирует оба раздела в
  `/media/jr/`. Работе не мешает, обрыв питания карта пережила. Отключается одним
  udev-правилом, см. `docs/udev-automount.md`. Правило не применено.
* **Полная проверка ext4 каждую 5-ю загрузку.** На 3.6 ТБ занимает около двух
  минут и выглядит как зависание. Снимается `tune2fs -c 0 /dev/nvme0n1p1`.
  Не применено.
* **Вход в спасательную систему.** Там root с коротким заводским паролем и
  разрешённым входом по паролю. Система теперь может подниматься сама при сбое
  загрузки, поэтому вход стоит перевести на ключ и пароль сменить. Не применено.
* **Батареи ИБП.** Мертвы, см. `docs/ups-2026-09-18.md`. До замены любое мигание
  сети равно жёсткому обрыву питания.
