NVMe handoff: SD-карта остаётся в слоте, система грузится с NVMe
=================================================================
Настроено 2026-09-18 на Orange Pi 5 Max.

ЗАЧЕМ
-----
После резкого отключения питания Samsung 990 PRO 4TB около 7.5 секунд
восстанавливает свои внутренние таблицы и только потом отвечает на первую
команду. NVMe-драйвер U-Boot ждёт ответа 6 секунд и не повторяет попытку.
Поэтому загрузчик из SPI-флеша (вендорский U-Boot 2017.09) NVMe не видел,
и плата "висла". Каждое следующее выключение кнопкой снова было "грязным"
для диска, поэтому помогала только загрузка Linux с SD и штатное выключение.

КАК ЭТО РАБОТАЕТ ТЕПЕРЬ
-----------------------
1. Карта в слоте: управление получает U-Boot 2025.04 с карты (не из SPI).
2. Его скрипт /boot/boot.scr включает питание слота NVMe, ждёт 5 секунд,
   затем до 6 раз пробует увидеть диск. Как только диск читается, грузит
   Ubuntu через её собственный /boot/extlinux/extlinux.conf на NVMe.
   Ядро, initrd и параметры берутся с NVMe: на карте ничего синхронизировать
   не нужно, обновления ядра Ubuntu подхватываются сами.
3. Если NVMe так и не прочитался, стартует спасательный Armbian с карты.
   Служба nvme-handoff-recover ждёт, пока Linux увидит диск, и делает
   чистую перезагрузку (это и есть прежняя ручная процедура). Не больше
   3 попыток подряд, потом система остаётся в спасательном режиме.
NVMe из спасательной системы никогда не монтируется и не пишется.

ФЛАГИ (пустые файлы в корне этого раздела HANDOFF)
--------------------------------------------------
  force-sd  или force-sd.txt   всегда грузить спасательную систему с карты
  try-nvme-once                вместе с force-sd: один раз загрузить NVMe,
                               U-Boot сам удаляет этот файл перед попыткой
  dry-run                      проверить NVMe, но загрузить спасательную систему
Нет флагов = обычный режим, грузится Ubuntu с NVMe.

С Mac: вставить карту, на томе HANDOFF создать пустой файл force-sd.txt.
Из Ubuntu (рабочий стол сам монтирует раздел в /media/jr/HANDOFF):
  touch /media/jr/HANDOFF/force-sd && sync && sudo reboot
  если раздел не смонтирован:
  sudo mount /dev/disk/by-label/HANDOFF /mnt && sudo touch /mnt/force-sd \
    && sudo umount /mnt && sudo reboot
Из спасательной системы (root@..., утилита уже установлена):
  nvme-handoff status | auto | force-sd | once | dry-run

ДИАГНОСТИКА
-----------
  nvme-retry.txt (здесь же)   пишет U-Boot, если диск ответил не с первой попытки
  /var/lib/nvme-handoff/recover.log на карте   журнал автоматических перезагрузок
  В спасательной системе: cat /proc/cmdline  (nvme_handoff=..., nvme_tries=...)

ЕСЛИ ВЫНУТЬ КАРТУ
-----------------
Плата грузится по-старому: SPI U-Boot 2017.09 -> NVMe. Работает, пока диск
был выключен штатно; после обрыва питания снова понадобится эта карта.

ОТКАТ
-----
В спасательной системе:
  cp /boot/boot.cmd.armbian-orig /boot/boot.cmd
  mkimage -C none -A arm -T script -d /boot/boot.cmd /boot/boot.scr
  systemctl disable nvme-handoff-recover
Резервные копии (скрипт, таблица разделов, дамп SPI): /root/nvme-handoff-backup

ЗАМЕЧАНИЯ
---------
* Спасательную систему без нужды не обновлять (apt upgrade может пересобрать
  boot.scr). После обновления проверить: nvme-handoff status, наличие блока
  "NVMe handoff" в /boot/boot.cmd.
* Проверено 2026-09-18 на живом железе, включая НАСТОЯЩИЙ обрыв питания
  (выдернули ИБП, он мгновенно снял выход). После обрыва диск снова готовился
  7.07 с, U-Boot прочитал его с первой попытки благодаря паузе 5 с,
  спасательный режим не понадобился. Ядро стартовало через 36 с после обрыва,
  82 из 82 контейнеров поднялись, Postgres восстановился штатно.
  Плюс до этого: сухой прогон и штатная загрузка через U-Boot с карты.
* Причина того обрыва - мёртвые батареи ИБП, а не сбой платы. Пока батареи
  не заменены, любое мигание сети для сервера равно жёсткому обрыву.
* Полная проверка ext4 на 3.6 ТБ идёт каждую 5-ю загрузку и занимает ~2 мин.
  Выглядит как зависание. Во время неё питание не передёргивать.
